# Обновления: stable и beta

Два контейнера приложения с **общей базой и файлами**: `app` (stable, все пользователи) и `app-beta`
(новая версия для части людей). Пользователи заходят как обычно на адрес stable; тех, у кого в админке
выбран канал «beta», stable сам незаметно передаёт в beta-контейнер. Если beta не запущена или упала,
эти люди просто работают на stable.

Фоновые задачи (сроки, уведомления, Telegram-бот, сводки) выполняет только stable.

## Выкатить новую версию

1. Скачайте новую версию: каждый релиз публикуется и с тегом `beta`
   (`ghcr.io/loktionov-g-bit/alexandria-planner:beta`), поэтому достаточно
   `docker compose --profile beta pull app-beta`. Свою сборку можно пометить тегом `beta` вручную.
2. Запустите beta: `docker compose --profile beta up -d app-beta`.
   При старте beta сама делает **бэкап базы** (`/data/backups/pre-…`) и применяет миграции.
   Миграции только добавляют поля и таблицы, поэтому stable продолжает работать на той же базе.
3. В Планере: **Администрирование → Обновления**. Переведите на beta себя, отдел или всех.
4. Всё хорошо → новая версия становится stable:
   в `.env` укажите `PLANNER_TAG=<номер версии>` (например `0.2.0`) и выполните `docker compose up -d app`,
   затем «Вернуть всех на stable» и `docker compose stop app-beta`.

## Откатить

**Администрирование → Обновления → «Вернуть всех на stable»**. Без простоя: следующий же запрос
каждого пользователя уходит на stable. Затем `docker compose stop app-beta`.

## Бэкапы перед миграциями

Хранятся в томе данных, `/data/backups`, последние 10 (`PLANNER_BACKUP_KEEP`).
Восстановление PostgreSQL: `pg_restore --clean --no-owner -d <база> pre-<версия>-<время>.dump`.
