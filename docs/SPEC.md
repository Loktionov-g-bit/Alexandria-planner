# Alexandria Planner — спецификация

Продуктовые требования и принятые решения. В коде на разделы ссылаются как «SPEC §N».

Отдельная программа концерна Alexandria. Open source.
- Название по-русски: **Alexandria Планер** (по-английски Alexandria Planner). Слово «планировщик» в этом документе означает только фоновые задачи (эскалация, автозакрытие).
Цифровая замена бумажных стикеров «сотрудник → руководитель», задачи сортируются по матрице Эйзенхауэра (важно/срочно).

## 1. Пользователи и роли
- Сейчас: 1 руководитель, 3 сотрудника. Проектировать с расчётом на крупные компании: много руководителей, отделов и сотрудников.
- Роли (минимум): руководитель, сотрудник.
- По умолчанию сотрудник видит только свои стикеры.
- Руководитель может открыть стикер другим сотрудникам (кнопка «поделиться» / «открыть доступ»).
- Задача может быть адресована нескольким сотрудникам.

## 2. Квадрант и сроки
- Сотрудник при создании ставит отметки «срочно» (да/нет) и «важно» (да/нет): это его оценка.
- Окончательное решение принимает руководитель: подтверждает квадрант или переносит стикер в другой. Сотрудник видит итоговый квадрант.
- Позже: статистика расхождений между оценкой сотрудника и решением руководителя.
- Дедлайн необязателен. Ставит сотрудник, руководитель может изменить.
- Когда до дедлайна остаётся N дней (настраивается, по умолчанию 2), стикер автоматически становится «срочным» и уходит в срочный квадрант. Руководитель получает уведомление.
- Просроченные стикеры выделяются цветом.
- «Важность» автоматически не меняется никогда, только человеком.

## 3. Жизненный цикл стикера
Статусы:
1. **Новый**: создан сотрудником, лежит во входящих руководителя, не разобран.
2. **Разобран**: руководитель посмотрел и назначил квадрант; автор видит, что стикер прочитан.
3. **В работе**: руководитель взялся за стикер.
4. **Нужно уточнение**: стикер возвращён автору с вопросом; после ответа автора снова у руководителя. Внутри стикера лента комментариев.
5. **Делегирован**: перепоручен другому сотруднику; тот отчитывается, руководитель принимает или возвращает на доработку.
6. **Решён**: ответ и итог (*согласовано / отклонено / выполнено / к сведению*); уходит автору и всем подключённым.
7. **Закрыт**: автор подтвердил получение; иначе автоматически через N дней.
8. **Отложен / Отклонён**: отложить до даты (стикер сам всплывёт) или отклонить с причиной.

Дополнительно:
- Вложения в стикере и комментариях (фото, PDF, документы).
- Журнал аудита: кто, когда и что изменил (статус, квадрант и т.д.).
- Автор может отозвать стикер, пока тот не разобран.
- Автор может переоткрыть решённый или закрытый стикер с комментарием; история сохраняется.

```
Новый → Разобран → В работе ⇄ Нужно уточнение
                       ↓ ↘
                       ↓   Делегирован → (принят / на доработку)
                       ↓
                    Решён → Закрыт  (↺ переоткрыт)
Разобран → Отложен (↺ всплывает в дату) / Отклонён
```

## 4. Интерфейс, поставка, уведомления
Поставка:
- Docker: устанавливается одной командой (`docker compose up`). Бот и уведомления внутри того же стека, без отдельной установки.

Интерфейс:
- Главный экран: 4 квадранта, стикеры выглядят как настоящие бумажные стикеры.
- Клик по стикеру открывает его крупно: полный текст, автор, история, комментарии, вложения.
- На стикере всегда видно, от кого он.

Авторизация:
- Обязательна система входа с ролями и правами.

Уведомления:
- Без жёсткой привязки к одному мессенджеру: подключаемые «каналы уведомлений».
- Обязательные: уведомления в браузере, Telegram.
- Каналы для других компаний: WhatsApp, email и другие.
- Пользователь сам в профиле привязывает свои каналы и выбирает, куда получать уведомления.

Телефон:
- Адаптивный сайт и PWA (можно «установить» на телефон как приложение), без отдельных нативных приложений.

Действия из мессенджера:
- Не только уведомления, но и действия: создать стикер, ответить на уточнение, подтвердить получение.

Авторизация (v1):
- Свои логины и пароли. Корпоративный вход (LDAP/AD, Google/Microsoft) позже.

Сеть:
- Сервис доступен из интернета (руководители в разъездах), поэтому HTTPS и усиленная безопасность обязательны.

HTTPS и прокси:
- Универсально: приложение должно корректно работать за любым внешним обратным прокси (Synology DSM, nginx, Traefik и т.д.), учитывать X-Forwarded-* и настраиваемый базовый URL.
- Встроенный Caddy с Let's Encrypt — опция (отдельный профиль compose), а не обязательная часть.

Безопасность:
- 2FA (TOTP: Google Authenticator и аналоги): обязательна для руководителей и администраторов, по желанию для сотрудников.
- Требования к сложности пароля.
- Ограничение попыток входа и временная блокировка.
- Журнал входов (кто, когда, откуда).

Создание стикеров из Telegram:
- Личка с ботом: сообщение → стикер.
- Бот в рабочем групповом чате: сообщение с пометкой → стикер.
- В обоих случаях автор — пользователь системы, привязанный к Telegram-аккаунту; от непривязанных бот не принимает стикеры.

Telegram, принцип:
- **Никакого центрального бота и сервера автора проекта.** Каждая компания создаёт своего бота через @BotFather и вводит его токен в админке (или в мастере первого запуска; шаг можно пропустить). Сообщения идут напрямую между сервером компании и Telegram.
- Токен хранится только на сервере компании, в UI показывается замаскированным.
- То же для всех каналов: ключи SMTP, WhatsApp и т.д. вводит сама компания. Проект ни от каких внешних сервисов автора не зависит.
- В админке есть пошаговая инструкция «как создать бота» и кнопка «проверить подключение».

Telegram для руководителя (полный разбор стикеров):
- Новый стикер приходит карточкой: автор, текст, оценка квадранта автором, дедлайн, вложения.
- Кнопки под карточкой: квадрант (4 кнопки), «В работу», «Уточнить» (бот просит текст вопроса), «Делегировать» (список сотрудников), «Решить» (итог: согласовано / отклонено / выполнено / к сведению + текст), «Отложить» (завтра / через неделю / дата), «Отклонить» (с причиной).
- Команды: `/inbox` (неразобранные), `/board` (стикеры по квадрантам), `/stats` (краткая сводка).
- Фото и файлы, отправленные боту, прикрепляются к стикеру.

Утренняя сводка руководителю:
- Ежедневно в настраиваемое время (по умолчанию 08:00, только рабочие дни; часовой пояс пользователя).
- Содержимое: число неразобранных во «Входящих»; число стикеров в «срочно+важно»; просроченные; отложенные, всплывающие сегодня; дедлайны сегодня и завтра; делегированные, ждущие приёмки.
- Кнопки быстрого перехода: «Входящие», «Срочно+важно», «Просроченные».
- Если всё пусто: короткое «Всё разобрано» (или не отправлять, на выбор пользователя).
- Отправляется по каналам пользователя (Telegram, Web Push, позже Email). Время, дни и сама сводка настраиваются в профиле.

Сводка по времени суток (в интерфейсе, шапка доски):
- Приветствие и сводка меняются по времени пользователя: **утро** 05–12 (Доброе утро: что ждёт сегодня), **день** 12–18 (Добрый день: что сделано с утра до текущего момента), **вечер** 18–23 (Добрый вечер: итоги дня), **ночь** 23–05 (Доброй ночи: итоги прошедшего дня).
- Один и тот же блок, меняются только период и показатели.
- Вечерняя сводка (итоги дня) может отправляться в Telegram так же, как утренняя (настраивается, по умолчанию выключена).

Telegram для сотрудника:
- Создать стикер (текст, фото, файлы), ответить на уточнение, подтвердить получение ответа, отчитаться по делегированному, отозвать или переоткрыть стикер.

Привязка и безопасность Telegram:
- Привязка аккаунта только из веб-профиля после входа (с 2FA): одноразовая ссылка или код для бота.
- Бот принимает действия только от привязанных аккаунтов; у каждого действия те же права, что в вебе.
- Отвязать можно из профиля, администратор может отвязать любого (например, при потере телефона).

Telegram, детали:
- В группе стикер создаётся командой (например, `/stiker текст`).
- В группе бот пишет только «Стикер №N создан». Дальнейший ход (статусы, вопросы, решение) идёт в личку автору.

## 4а. Экраны
**У каждого пользователя (руководитель и сотрудник) своя доска из 4 квадрантов** с перетаскиванием и панелью «Входящие» (неразобранные).
- У руководителя на доске: стикеры, адресованные ему.
- У сотрудника на доске: делегированные ему стикеры, групповые стикеры от руководителя, стикеры, адресованные лично ему.
- Отдельно у всех «Отправленные»: стикеры, созданные пользователем, с их статусом и итоговым квадрантом у получателя.
- **Квадрант на доске выставляет её владелец.** Сотрудник может переложить делегированный стикер в другой квадрант, но видит квадрант, который поставил руководитель, а руководитель видит, куда переложил сотрудник.
- **Личные стикеры**: можно создать стикер самому себе (задача, напоминание). Видит только автор.
- **Сотрудник → сотрудник**: стикеры коллегам напрямую, без руководителя.
- Цвет стикера по квадранту (красный / оранжевый / зелёный / серый); автор показан аватаркой и именем.
- В квадранте по умолчанию ~8 стикеров, отсортированных по дедлайну, остальные по клику «ещё N».
- Видимость стикеров «сотрудник → сотрудник» для руководителя: по умолчанию **не видит**, только обезличенная статистика (количество, время ответа внутри отдела); при необходимости подключается кнопкой «открыть доступ». Настройка в админке позволяет крупным компаниям включить просмотр (только чтение) всех стикеров внутри отдела.
- У стикера есть **заголовок** (короткий, обязательный) и **текст** (подробности).
- Стикер в маленьком виде (на доске): заголовок, от кого, оценка важности/срочности (автора, а если руководитель уже решил — его), срок.
- Стикер крупно: заголовок, полный текст, автор, дедлайн, обе оценки квадранта, комментарии, вложения, история, действия.

### Визуальный стиль
- Две темы: светлая и тёмная (по умолчанию как в системе, переключатель в профиле).
- Стикер — квадратный листок, как настоящий на столе: лёгкая тень, едва заметный наклон, фактура бумаги. Стол не рисуется буквально, только стилизованный намёк (фон, глубина).
- Анимации перетаскивания: листок «поднимается» (тень, масштаб), плавно ложится в новый квадрант, остальные стикеры раздвигаются.
- Стильно и сдержанно, без «колхоза»: аккуратная типографика, приглушённая палитра квадрантов, минимум декора.
- **Никаких бежевых тонов** (ни в интерфейсе, ни в отчётах): нейтральные холодные серые фоны, белая бумага.
- Макет доски: https://claude.ai/artifact/AwzcoWohcn6FinjkvusaS3 (копия исходника: `docs/mockup-board.dc.html`). Согласованное направление: мягкий стиль — скругления, мягкие тени, точечная сетка фона, шрифты Unbounded (заголовки) + Onest (текст), цветные аватарки авторов. Жёсткий «редакционный» стиль (линии, моноширинный шрифт, острые углы) пользователь отверг.
- Элементы макета, которые пользователю понравились: левая панель (навигация, блок сводки с полоской недели, профиль, тема); приветствие по времени суток с иконкой и фоновым «освещением» (утро/день/вечер/ночь); кольцо прогресса «разобрано X из Y»; карточки показателей; «Входящие» стопкой веером; матрица с подписями осей и иконками квадрантов; открытый стикер из двух частей (листок + панель «ход стикера», квадрант, действия).
- Стикеры висят «хаотично»: наклон от −3° до +3°, разная высота, разные крепления — скотч, washi-скотч (синий/мятный/розовый), скотч по углам, канцелярские кнопки разных цветов, магниты. Способ крепления стабилен для конкретного стикера.
- **Красная кнопка — только у просроченных стикеров.**
- **Скрепку не использовать никогда.**
- Выделение текущего дня в полоске недели — мягкое (лёгкая подложка и тонкое кольцо), не броское.
- Много стикеров в квадранте: при > 4 компактный режим (листки 142 px); при > 8 видны 7 + «стопка +N», по клику раскрываются все; сортировка: просроченные, затем по сроку.
- Анимации учитывают системную настройку «уменьшить движение».
- Архив (закрытые и отклонённые) с поиском. Статистика.
- Администратор: пользователи, отделы, роли, каналы и бот, обновления, журнал входов, настройки.
- Профиль: пароль, 2FA, Telegram, уведомления, утренняя сводка, язык, часовой пояс.

## 5. Оргструктура и адресация
- Сотрудники привязаны к отделам; у отдела есть руководитель.
- Если адресат не указан, стикер уходит руководителю своего отдела.
- Сотрудник может адресовать стикер другому руководителю.
- **Групповые стикеры**: от отдела к отделу, от руководителя всему отделу. В общем списке помечаются отдельно.
  - *Руководитель → свой отдел*: у каждого сотрудника свой статус («прочитал / выполнил»). Руководитель видит сводку (кто прочитал, кто нет). Квадрант назначает руководитель.
  - *Отдел → отдел*: стикер попадает во входящие руководителю отдела-получателя, дальше обычный цикл (разбор, квадрант, делегирование). Ответ видят автор и руководитель отдела-отправителя.
  - На доске групповые отличаются цветом или иконкой, есть фильтр «только групповые».

## Роли
- **Администратор**: заводит отделы и пользователей, настраивает каналы уведомлений и Telegram-бота. Не видит содержимое стикеров. Роль может быть совмещена с ролью руководителя (маленькая фирма) или отдельной (IT в крупной компании).
- **Руководитель**: разбирает стикеры, назначает квадранты, делегирует, решает, открывает доступ к стикерам, создаёт групповые стикеры.
- **Сотрудник**: создаёт стикеры, отвечает на уточнения, выполняет делегированное, подтверждает получение ответа.

## 6. Связь с Alexandria
- В v1 программа полностью автономна. Интеграцию с другими проектами концерна рассмотрим в будущем.

## 7. Статистика
- Сколько стикеров и от кого.
- Среднее время ответа (и по этапам).
- Сколько стикеров висит в каждом квадранте.
- Расхождение оценки квадранта сотрудником и руководителем.
- **Выгрузка отчётов в Excel (.xlsx)**, без бежевых цветов. **Шаблон утверждён пользователем 2026-10-31** (PDF-превью: `docs/report-sample.pdf`). Образец: `docs/report-sample.xlsx`, генератор образца: `docs/report-sample-generator.py` (openpyxl). Шаблон:
  - Общее оформление: без сетки Excel, шапка листа (надпись «ALEXANDRIA · ПЛАНЕР», крупный заголовок, подзаголовок с отделом и периодом, жирная линия), заголовки таблиц тёмные (#16191E) с белым текстом, чередование строк светло-серым (#F4F6F9), тонкие разделители, альбомная ориентация с печатью по ширине страницы.
  - Лист **«Сводка»**: 4 крупных показателя (всего, решено, в работе, просрочено — красным), таблица распределения по квадрантам с их цветами и долями (формулы), горизонтальная диаграмма в цветах квадрантов, неразобранные и среднее время до решения.
  - Лист **«Стикеры»**: все стикеры за период (№, заголовок, автор, исполнитель, квадрант с заливкой цвета, оценка автора, создан, срок, решён, статус, итог). Просроченные сверху и выделены красным; расхождение оценки автора выделено фиолетовым. Автофильтр, закреплённые шапка и колонка №.
  - Лист **«По сотрудникам»**: отправил, решено, среднее время ответа, расхождения оценок и их доля, строка «Итого» на формулах.
  - Выгрузка за выбранный период (день, неделя, месяц, произвольный), по отделу или сотруднику.

### Анализ аналогов (2026-10-31)
Точного аналога не найдено. Ближайшие: Priority Matrix (платный SaaS для команд, без self-hosted и Telegram), Asana / Shtab / Kaiten (таск-трекеры с видом-матрицей, задачи сверху вниз, облако), open-source матрицы на GitHub (только для одного пользователя), самосборные Telegram-боты с одобрением (без матрицы и интерфейса). Отличия проекта: поток снизу вверх (сотрудник → руководитель), своя доска у каждого и передача стикеров с жизненным циклом, self-hosted и open source со своим ботом у каждой компании, полноценная работа из Telegram, «живые» стикеры.

## 8. Технический стек
Единый с Alexandria (упрощает будущую интеграцию).

- **Бэкенд**: Python 3.12, FastAPI, SQLAlchemy 2 + Alembic, Pydantic.
- **Авторизация**: свои сессии в httpOnly-cookie, argon2, TOTP 2FA (`pyotp`), ограничение попыток.
- **Реалтайм**: WebSocket (доска обновляется без перезагрузки).
- **БД**: PostgreSQL 16.
- **Фон** (тот же код и образ): планировщик (эскалация по дедлайну, автозакрытие, всплытие отложенных), Telegram-бот (свой лёгкий клиент Bot API на httpx вместо aiogram — решение 2026-11-01: меньше зависимостей, проще тесты; long polling), рассылка уведомлений.
- **Уведомления**: единый интерфейс каналов. v1: Web Push, Telegram, Email (SMTP), Webhook. Позже: Apprise, WhatsApp Business API.
- **Фронтенд**: React + Vite + TypeScript, `dnd-kit` (перетаскивание), TanStack Query, PWA (`vite-plugin-pwa`), i18n.
- **Языки**: русский, английский, немецкий, чешский, белорусский, казахский, грузинский (решение 01.11.2026). Источник — русский; словари интерфейса `frontend/src/locales/*.json`, тексты сервера (уведомления, бот, Excel) `backend/app/i18n/*.json`, руководство `docs/guide/*.html`. Новые пользователи получают язык администратора, каждый меняет его в профиле. Названия продукта: Planner (en), Planer (de), Plánovač (cs), Планер (ru/be/kk), პლანერი (ka).
- **Файлы**: v1 — Docker-том; позже — S3-совместимое хранилище (опция).
- **Поставка**: один образ (app + worker) + postgres в `docker-compose.yml`; образы amd64 и arm64; Caddy — необязательный профиль; публикация в GHCR через GitHub Actions.
- **Лицензия**: MIT.

### Требования к ресурсам
Система должна быть лёгкой, у пользователей разное железо.
- По умолчанию app, бот и планировщик работают в одном процессе и одном контейнере. Для крупных инсталляций их можно разнести (флаг в env) и масштабировать.
- Целевой бюджет: весь стек в простое ≤ 512 МБ RAM, работает на 1–2 ядрах и на ARM-NAS (≥ 1 ГБ RAM).
- PostgreSQL с урезанными настройками памяти по умолчанию.
- Фронтенд собирается в статику и отдаётся тем же бэкендом (без отдельного nginx-контейнера).
- Без Redis и брокеров очередей в v1: фоновые задачи через БД.

## 10. Обновления: stable / beta (канареечный выпуск)
Цель: новая версия сначала у узкого круга, затем у всех; при проблемах всех можно вернуть на стабильную без простоя.

- Одновременно работают два контейнера приложения, `stable` и `beta`, с **общей базой данных** (данные одни, стикеры видны всем).
- Администратор назначает **канал обновлений** пользователю или отделу: stable или beta.
- Маршрутизация: после входа пользователь получает cookie канала, лёгкий маршрутизатор направляет его запросы в нужный контейнер.
- Пользователь beta видит в интерфейсе пометку «тестовая версия».
- **Выкатка**: все переводятся на beta, затем beta становится новой stable.
- **Откат**: перевод пользователей обратно на stable, одной кнопкой и без простоя.
- Миграции БД только **совместимые с предыдущей версией** (expand/contract): сначала добавляем, старое удаляем только через релиз. Иначе stable сломается на новой схеме.
- Перед каждой миграцией автоматический бэкап БД.
- Фоновые задачи (планировщик, рассылка) выполняет только один экземпляр (блокировка в Postgres).
- Telegram-бот: один токен может опрашивать только один экземпляр, поэтому бот работает на stable. Для тестирования изменений в боте используется отдельный тестовый бот с отдельным токеном.
- Когда beta не запущена, работает один контейнер: бюджет ресурсов не меняется.
- Образы: теги `:stable`, `:beta` и точные версии (`:0.1.3`).

### Самообновление (как в Alexandria)
- Система сама следит за **GitHub Releases** проекта (публичный API, без токена; периодичность настраивается, по умолчанию раз в 6 часов). Источник обновлений настраивается, чтобы форки могли указать свой репозиторий.
- Найдена новая версия → администратору уведомление в браузере и в Telegram: номер версии, список изменений, кнопки.
- Сценарий кнопок:
  1. «Установить в beta» → система скачивает образ, делает бэкап БД, применяет миграции, поднимает beta-контейнер.
  2. «Перевести всех на новую версию» → новая версия становится stable.
  3. «Откатить» → все обратно на прежнюю stable.
  - Для маленьких компаний без беты: кнопка «Обновить сразу».
- **Автоматическая проверка здоровья**: если новый контейнер не прошёл healthcheck за отведённое время, установка отменяется сама, админ получает уведомление с причиной.
- **Безопасность**: доступ к Docker есть только у отдельного маленького контейнера `updater`, а не у приложения. Приложение может попросить его лишь о фиксированном наборе действий (скачать версию X, запустить или остановить beta, повысить, откатить) по внутренней сети с секретным ключом. Обновляться можно только образами из настроенного репозитория.
- Самообновление можно выключить (тогда обновление вручную через `docker compose pull`).

### Среды
1. **dev/test**: сырые изменения, тестовые данные, отдельный тестовый Telegram-бот.
2. **beta**: новая версия для бета-группы, общая база со stable.
3. **stable**: рабочая версия для всех.

Путь изменения: dev/test → beta (часть сотрудников) → stable (все).
